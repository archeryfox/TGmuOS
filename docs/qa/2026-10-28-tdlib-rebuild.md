# QA-2026-10-28-001: пересборка и установка TDLib для muOS

- **Статус:** сборка и установка выполнены; авторизация Telegram требует отдельного подтверждения
- **Компоненты:** TDLib, TGMUOS, AArch64 toolchain
- **Устройство:** RG35XX SP / muOS

## Исправленные ошибки кросс-сборки

1. Проверка C++ toolchain падала на отсутствующем заголовке `<atomic>`. Для
   сборки предоставлены AArch64 заголовки libstdc++ и target libraries из
   Fedora RPM в отдельном build SDK; файлы системной среды и проекта не
   изменялись.
2. При cross-configure TDLib не создавала несколько исходников генератора.
   Host-сборка TDLib выполнила `prepare_cross_compiling`, после чего target
   сборка продолжилась.
3. В build SDK отсутствовал ожидаемый путь OpenSSL headers. Он был направлен
   на заголовки OpenSSL из подготовленных target dependencies.
4. SDL2_ttf из muOS sysroot имела транзитивные shared-library зависимости,
   которых не было в локальном SDK. При линковке приложения использован
   `--allow-shlib-undefined`; фактический запуск затем проверен на устройстве.

Все временные toolchain/SDK файлы и промежуточные сборки лежат в `/tmp`.
Они не являются переносимым build-рецептом и не входят в репозиторий.

## Артефакты и проверка

- TDLib: официальный commit
  `ea3f69ce11aef458bfbb09869b809ede4447486f`, собранная библиотека
  `libtdjson.so.1.8.69`, 65,583,096 bytes.
- Библиотека — ELF64 AArch64; `DT_NEEDED`: только `libm.so.6` и `libc.so.6`;
  максимальный GLIBC symbol version — 2.38.
- `tgmuos` собран для AArch64 с `-Wall -Wextra -Wpedantic -Werror`.
- На устройстве старые файлы сохранены как
  `tgmuos.backup-tdlib-20261027T222131Z` и
  `lib/libtdjson.so.backup-tdlib-20261027T222131Z`. Новые файлы заменены
  атомарным rename.
- После перезапуска TGMUOS процесс работает и `/proc/<pid>/maps` показывает
  установленную новую `libtdjson.so`. Прежняя ошибка несовместимости в
  `log.txt` не обнаружена.
- При повторной проверке текущий `log.txt` содержит отказ TDLib на запросе
  `setTdlibParameters`: `400: Valid api_id must be provided`. Приватный
  `telegram.conf` совпадает с указанным пользователем файлом в проекте,
  формат api_id/api_hash проходит локальную проверку, а launcher передаёт его
  путь приложению; значения не выводились и не менялись. TDLib всё равно
  отклоняет параметры, хотя пользователь сообщает об успешной авторизации и
  загрузке чатов в прежнем запуске. Копирование того же файла это не исправит;
  нужно искать различие в новой сборке/запросе или в контексте прошлой сессии.
- Текущий `sing-box.log` пуст (0 bytes), процесс sing-box жив; локальный
  SOCKS5 greeting на `127.0.0.1:10808` отвечает `05 00`. Это подтверждает
  локальный listener, но не успешный выход через удалённую Reality-ноду.
- Права `telegram.conf` восстановлены до `0600`; содержимое не изменялось.
- Текущий перезапуск не оценивался длительно и чаты повторно не сверялись.
  Пользователь сообщает, что предыдущий запуск уже входил в его аккаунт и
  загружал чаты, но был нестабилен, поэтому пользователь завершил приложение.
  Regression tests в этой сессии не запускались.

## Сопутствующее наблюдение по прокси

Приложение и sing-box запущены, однако диагностика конфигурации подписки
показала отказ Reality handshake для всех 13 узлов. Это отдельно от ошибки
TDLib и может мешать сетевой авторизации. Симптомы совпадают с описанной в
[upstream issue sing-box #4520](https://github.com/SagerNet/sing-box/issues/4520)
проблемой новых Xray REALITY-серверов; версии серверов подписки независимо не
подтверждались. Подробности и координация без секретов ведутся в
[`docs/aichat`](../aichat/2026-10-28.md).
