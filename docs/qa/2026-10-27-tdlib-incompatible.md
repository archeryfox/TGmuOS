# QA-2026-10-27-001: TDLib устарела — клиент не может авторизоваться

- **Статус:** исправлена заменой TDLib 2026-10-28; вход в аккаунт отдельно не подтверждён
- **Серьёзность:** blocker
- **Компонент:** runtime-зависимость `lib/libtdjson.so` (TDLib v1.8.0)

## Симптом

Приложение на устройстве стартует штатно (framebuffer открыт, первый кадр
отрисован, контроллер виден), но TDLib неработоспособна.

## Доказательства

Устройство `anbernic`, `/mnt/mmc/MUOS/application/tgmuos/log.txt`:

```
tgmuos starting
External keyboards detected: 0
Opened controller: muOS-Keys
Framebuffer: 640x480, 32 bpp, stride 2560
Using font: res/fonts/AdwaitaSans-Regular.ttf
UI ready; press ESC to quit
First frame rendered on screen 0
TDLib: This TDLib version is incompatible; rebuild it for the current API
```

Процессы на момент проверки: `mux_launch.sh` → `run-client.sh` →
`sing-box run` + `tgmuos` (PID 23488) — все живы, sing-box поднял SOCKS5.

## Причина

TDLib v1.8.0 (собрана 2026-10-26 для AArch64) отвергнута текущим API
Telegram. Диагностика из сессии «Fixing Telegram Startup» (mismatch
`setTdlibParameters`) устранялась под схему НОВЫХ версий TDLib — фактически
бинарник v1.8.0 не соответствует схеме и серверу одновременно.

## Ожидаемое поведение

После старта в логе: загрузка libtdjson.so без ошибки, состояние
`authorizationStateWaitPhoneNumber` (или QR). На экране — экран входа,
а не вечный статус инициализации.

## Результат фикса (2026-10-28)

- Сборка TDLib и приложения для AArch64 завершилась успешно; детали и ошибки
  кросс-сборки описаны в [QA-2026-10-28-001](2026-10-28-tdlib-rebuild.md).
- Установка выполнена через штатный launcher с timestamped-бэкапами и
  атомарной заменой. TGMUOS запущен, а `/proc/<pid>/maps` подтверждает, что
  процесс загрузил новую `libtdjson.so`.
- В `log.txt` после перезапуска не найдена прежняя ошибка несовместимости.
- Поведение авторизации и показа чатов в этом перезапуске отдельно не
  проверялось. Пользователь уточнил, что в предыдущем запуске клиент успешно
  вошёл в его аккаунт и загрузил чаты, но работал нестабильно; пользователь
  завершил работу клиента. Текущая сборка должна оцениваться также по
  стабильности, а не только по совместимости TDLib.

## QA-2026-10-27-002: telegram.conf доступен на чтение всем

`/root/.config/tgmuos/telegram.conf` имеет права `755` при требуемых `600`
(содержит api_id/api_hash). Устраняется вместе с выкладкой фикса.

### Ответ фиксера (2026-10-27)

Исправлено до выкладки TDLib: свежий `telegram.conf` установлен на устройство
по приватному пути `/root/.config/tgmuos/telegram.conf` (права `600`, владелец
root, каталог `700`); целостность сверена по md5 (совпадение, значение не
публикуется). Читаемая для всех копия с exFAT-раздела приложения удалена —
лаунчеры (`mux_launch.sh`, `TGMUOS.sh`) предпочитают приватный путь при
наличии. Статус: **fixed, требует подтверждения тестировщиком**.

## QA-2026-10-27-001: ход работы фиксера (2026-10-27)

- Сборочная среда прошлой сессии утеряна (/tmp очищен, контейнер `telesp-build`
  отсутствует) — восстановлена с нуля: sysroot из библиотек устройства
  (glibc 2.38) + Fedora aarch64 `glibc-devel`/`kernel-headers`, заголовки
  SDL2 2.28.5 / SDL2_ttf 2.22.0 из исходников под версии библиотек устройства.
- Фиксы сборки: `preferences.c` (format-truncation, gcc 14), `telegram.c`
  (unused `log_debug()`) — коммит `7736b2f`.
- TDLib: теги выше v1.8.0 в репозитории отсутствуют, актуальная версия —
  `master` (клонирован, коммит от 2026-10-22). Сборка AArch64 — нативно в
  контейнере `fedora:39` (glibc 2.38, совпадает с устройством) под qemu
  (binfmt), OpenSSL 3.3.2 и zlib 1.3.1 статически, `libstdc++`/`libgcc`
  статически. Идёт в фоне; результат — `lib/libtdjson.so` (stripped).
